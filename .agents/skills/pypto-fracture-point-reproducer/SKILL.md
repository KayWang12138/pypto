# PyPTO 断裂点复现与 Skill 优化

基于断裂点报告，系统性复现问题场景、分析责任归属、并优化相关 skill。

---

## 核心原则

> 严格遵循以下原则。

1. **先复现，再分类，再优化**
   - 必须先验证断裂点是否可复现，再进行后续工作。
   - 无法复现的断裂点需明确标注原因。

2. **分类基于证据，不凭经验推断**
   - 检查官方文档是否有相关说明。
   - 文档有说明但仍出问题 → skill
   - 文档无说明 → 文档
   - 框架设计缺陷 → 框架

3. **只优化属于 skill 的断裂点**
   - 属于框架的问题 → 报告建议，不修改代码
   - 属于文档的问题 → 报告建议，不修改代码
   - 属于 skill 的问题 → 查找合适位置并优化

4. **优化必须严谨、高效、清晰、风格与修改文件类似**
   - 引用官方文档作为依据。
   - 提供错误示例和正确写法。
   - 给出具体可操作的解决方案。

---

## 工作流程

### 阶段一：断裂点筛选

#### 步骤 1：读取断裂点报告

读取用户指定的断裂点报告文件，提取以下信息：

| 字段 | 用途 |
|------|------|
| 断裂点编号（FP-XXX） | 问题标识 |
| 问题类型 | 分类参考 |
| 实体名称 | 涉及的 API/模块 |
| 证据片段 | 复现依据 |
| 复现步骤 | 测试用例设计参考 |
| 错误信息 | 验证匹配 |

#### 步骤 2：筛选可复现断裂点

按以下标准筛选：

| 条件 | 说明 |
|------|------|
| 有示例代码 | 优先处理有完整代码片段的断裂点 |
| 报错来源清晰 | 错误信息明确，可定位问题 |
| 非环境问题 | 不是环境配置导致的特殊问题 |

**筛选结果输出**：
```markdown
## 可复现断裂点清单

| 编号 | 问题 | 是否可复现 | 原因 |
|------|------|------------|------|
| FP-XXX | ... | 是/否 | ... |
```

---

### 阶段二：复现测试

#### 步骤 3：创建复现工作目录

在当前目录下创建 `fracture_point_reproduction/{report文件名}/` 目录，用于存放测试脚本和报告。

#### 步骤 4：编写最小复现用例

为每个可复现断裂点编写最小测试用例：

**用例结构**：
```python
"""
FP-XXX: [问题描述]

预期错误: [错误码/错误信息]
复现策略: [测试策略说明]
"""

import pypto
import torch
import torch_npu

def test_xxx():
    """测试用例"""
    # 1. 定义 kernel
    # 2. 准备数据
    # 3. 执行并捕获异常
    # 4. 判断是否复现
```

**关键要求**：
- 用例应该力求是最小可运行单元
- 能够输出清晰的测试结果

#### 步骤 5：执行复现测试

运行测试用例，记录结果：

| 结果 | 说明 |
|------|------|
| ✓ 已复现 | 测试失败，错误信息与报告匹配 |
| ✗ 无法复现 | 测试成功，问题可能在后续版本已修复 |
| ⚠️ 部分复现 | 问题存在但表现形式不同 |

---

### 阶段三：责任归属分类

#### 步骤 7：检查官方文档

针对每个已复现成功的断裂点，检查官方文档：

```bash
# 检查相关 API 文档
ls docs/api/operation/pypto-*.md
ls docs/api/controlflow/pypto-*.md
ls docs/tutorials/development/*.md
```

**文档检查项**：
- [ ] 是否有相关 API 文档
- [ ] 是否有约束说明
- [ ] 是否有使用示例
- [ ] 是否有错误处理说明

#### 步骤 8：分类判定

按以下规则判定责任归属：

| 条件 | 分类 | 处理方式 |
|------|------|----------|
| 框架设计不合理，非文档/skill能解决 | **框架** | 报告建议，不修改代码 |
| 文档无相关说明 | **文档** | 报告建议，不修改代码 |
| 文档有约束说明但不够突出/未提供解决方案 | **skill** | 查找合适位置优化 |

**分类判定流程**：
```
断裂点
  │
  ├─ 检查文档是否有说明？
  │   ├─ 否 → 文档
  │   └─ 是 → 继续
  │
  ├─ 约束是否足够突出？
  │   ├─ 否（埋在深处） → skill
  │   └─ 是 → 继续
  │
  ├─ 是否提供解决方案？
  │   ├─ 否 → skill
  │   └─ 是 → 继续
  │
  └─ 是否是框架设计问题？
      ├─ 是 → 框架
      └─ 否 → skill（用户仍遇到问题）
```

#### 步骤 9：输出分类结果

```markdown
## 断裂点责任归属分类

| 断裂点 | 问题 | 分类 | 依据 |
|--------|------|------|------|
| FP-XXX | ... | 框架/文档/skill | ... |
```

### 阶段四：Skill 优化

**仅针对分类为 skill 的断裂点执行此阶段。**

#### 步骤 10：定位优化位置

搜索现有 skill，找到最合适的优化位置：

```bash
# 列出所有 skill
ls .agents/skills/

# 搜索相关内容
grep -r "关键词" .agents/skills/*/SKILL.md
```

**优化位置选择原则**：

| 断裂点场景 | 推荐优化位置 |
|------------|--------------|
| 算子实现问题 | `pypto-op-develop/SKILL.md` |
| 精度问题 | `pypto-precision-debugger/SKILL.md` |
| 环境问题 | `pypto-environment-setup/SKILL.md` |
| API 使用问题 | `pypto-api-explorer/SKILL.md` |

#### 步骤 11：编写优化内容

优化内容必须包含：

1. **约束说明**：清晰说明限制条件
2. **错误示例**：展示错误写法
3. **正确写法**：展示正确写法
4. **解决方案**：提供具体解决方法
5. **依据引用**：引用官方文档

**优化内容模板**：
```markdown
### [约束名称]

**问题**：[问题描述]

**依据参考**：
- [官方文档路径]：[相关说明]

**错误示例**：
```python
# ❌ 错误写法
[错误代码]
```

**正确写法**：
```python
# ✅ 正确写法
[正确代码]
```

**最佳实践**：
1. [建议1]
2. [建议2]
```

#### 步骤 12：应用优化

修改对应的 SKILL.md 文件，确保：

- [ ] 优化内容放在合适位置（如"实现注意点"、"常见问题"章节）
- [ ] 保持与现有内容风格一致
- [ ] 不破坏现有内容结构
- [ ] 引用的文档路径正确

## 复现测试规范

### 测试用例命名

- `fp{编号}_{问题关键词}.py`
- 例如：`fp005_mixed_dtype.py`

### 测试结果判定

| 输出 | 含义 |
|------|------|
| `✓ REPRODUCED` | 已成功复现 |
| `✗ NOT REPRODUCED` | 无法复现 |
| `✓ SUCCESS` | 测试通过 |
| `✗ FAILED` | 测试失败 |

### 错误码匹配

| 报告错误码 | 说明 |
|------------|------|
| `FFFFFF` | 通用编译错误 |
| `FC0000` | 数据类型/约束错误 |
| `F21004` | Tile shape 错误 |
| `FC4000` | Cube/Matmul 配置错误 |
