# GitCode PR 代码检视标准

本标准用于指导 `gitcode-pr-review` skill 在 PyPTO 仓库上进行代码检视时的关注点和输出格式。

## 1. 总体原则

- **安全优先**：任何可能影响安全性、资源泄露的改动都必须优先指出。
- **正确性优先于性能**：先保证行为/结果正确，再考虑性能优化建议。
- **保持仓库风格一致**：命名、日志、异常处理方式与现有代码保持一致。
- **可读性与可维护性**：适当的抽象、清晰的边界和必要的注释。

## 2. C++ 代码（主要针对 `framework/` 等目录）

重点检查：

1. **资源管理**
   - 是否使用 RAII / 智能指针管理资源（内存、句柄、文件等）。
   - 是否存在 `new` / `malloc` 后未释放的路径。
2. **接口与边界**
   - 函数参数是否做了合法性校验（空指针、越界、非法枚举值等）。
   - 是否在模块边界上进行充分的错误码/异常处理。
3. **并发与线程安全**
   - 加锁范围是否合理，是否可能出现死锁或竞态条件。
   - 使用全局/静态变量时是否考虑多线程访问。
4. **const 正确性与易读性**
   - 能 `const` 的尽量 `const`，传参优先使用 `const &`。
   - 复杂逻辑是否拆分为更小的函数，避免超长函数。

## 3. Python 代码（`python/`、`models/` 等目录）

重点检查：

1. **异常处理**
   - 是否捕获了预期的异常类型，而不是无差别 `except Exception`。
   - 是否会默默吞掉异常，从而掩盖真实错误。
2. **类型与接口**
   - 关键函数是否添加了类型注解（特别是对外接口）。
   - 返回值是否稳定、文档化，避免隐式返回 `None`。
3. **性能与资源**
   - 是否存在明显的 N^2 循环、重复 IO、重复计算等可避免的开销。
   - 是否正确关闭文件/网络连接等资源。

## 4. 通用风格与结构

- 命名符合仓库惯例（如类名、函数名、宏名等保持一致风格）。
- 日志使用统一的日志接口/宏，并遵循现有日志级别划分。
- 错误处理路径清晰，不将错误静默丢弃。
- 注释聚焦于「为什么」，而不是复述代码的「做什么」。

## 5. 评论分级与格式

与 `SKILL.md` 中的规范保持一致：

- `🔴 必须修改`：影响功能、安全或编译通过的严重问题。
- `🟡 建议修改`：可维护性、性能、可读性等方面的非致命问题。
- `🟢 可选优化`：风格或微小优化，可按团队偏好处理。

评论格式示例：

```text
【🔴 必须修改】持锁调用 impl_->Stop() 可能导致死锁

当前实现在持有 mutex 的情况下调用 impl_->Stop()，而 impl_->Stop() 内部也可能尝试获取同一把锁，存在死锁风险。

建议：将 Stop 调用移动到锁外部，或在 impl_->Stop() 内部避免再次加锁。
```

---

## 6. 建议工作流

1. 先快速浏览整体 diff，锁定高风险文件（调度、资源管理、公共接口等）。
2. 再细致查看关键文件的 patch，逐条记录问题点及等级。
3. 在向用户展示检视清单时，明确区分必须修改和建议修改。
4. 仅在用户确认后，将对应条目通过 API 提交到 GitCode。
