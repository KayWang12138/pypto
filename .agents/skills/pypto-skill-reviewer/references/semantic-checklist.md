# 语义评审检查清单

本清单定义了需要 LLM 判断的 21 条语义规则。对每条规则，必须严格遵循对应的检查要求、证据标准与判定口径。

## 输出格式

对每条规则输出一个 JSON 对象：

```json
{
  "rule_id": "R07",
  "status": "FAIL",
  "severity": "S1",
  "dimension": "D1",
  "message": "(必须引用目标 skill 中的具体内容，禁止泛化描述)",
  "evidence": {
    "file": "SKILL.md",
    "line": 3,
    "snippet": "(必须是目标 skill 的逐字摘录，长度≥10字符)"
  },
  "suggested_fix": "(必须是针对该 skill 的具体可执行修改建议)"
}
```

对于 PASS 结果，将 `status` 设为 `"PASS"` 并提供简短 `message` 说明发现了什么。PASS 的 evidence 可选。

## D1 Frontmatter 元数据

### R07 — Description 必须回答“做什么”和“何时用”（S1）

**检查**：读取 frontmatter 的 `description` 字段，必须清晰回答：

1. **这个 skill 做什么？** —— 目标/产出
2. **什么时候使用？** —— 触发条件或用户场景

**证据标准**：引用 `description` 原文，并指出两点中哪一点缺失或表达不清。

**判定**：

- PASS：两点都回答了（显式或隐含但清晰）
- FAIL：缺失其一或两者都缺失

### R08 — Description 包含用户自然会说的触发短语（S2）

**检查**：`description` 应包含用户在想调用该 skill 时会自然说出口的短语/关键词（用于匹配意图）。

**证据标准**：引用 `description` 原文；如包含触发短语，列出它们；如不包含，给出应补充的短语示例。

**判定**：

- PASS：至少包含 1 个自然触发短语
- FAIL：仅有技术/正式表述，缺少用户侧触发短语

### R09 — Description 以结果为导向（S2）

**检查**：`description` 应强调用户能得到的结果，而不仅是罗列能力点。

**证据标准**：引用 `description` 原文，说明其更偏“结果”（例如“对 skill 打分并输出报告”）还是更偏“功能清单”（例如“解析 frontmatter、跑脚本、聚合 findings”）。

**判定**：

- PASS：以结果描述为主
- FAIL：以功能罗列为主且缺少明确结果

## D2 简洁性与效率

### R14 — 各章节不应出现冗余重复内容（S2）

**检查**：扫描 `SKILL.md` 各章节，是否存在实质性重复的内容（同一指令/段落在多处重复出现）。

**证据标准**：分别引用两处重复内容，并给出它们的章节标题与行号。

**判定**：

- PASS：未发现明显重复
- FAIL：同一指令或内容块在两个及以上位置重复

---

## D3 文件结构与导航

### R19 — 被引用文件必须说明用途与加载时机（S2）

**检查**：对 `SKILL.md` 中提到/链接到的每个文件（`references/`、`scripts/`、`templates/` 等），确认是否说明了：

1. **用途**：这个文件做什么
2. **加载时机**：何时读取/执行它

**证据标准**：逐个列出被引用文件，并引用其在 `SKILL.md` 中出现时的上下文；指出哪些文件缺少用途或时机描述。

**判定**：

- PASS：所有被引用文件都说明了用途与加载时机
- FAIL：至少有 1 个被引用文件缺少用途或时机信息

---

## D4 语言与表达

### R20 — 指令应使用祈使语气（S2）

**检查**：skill 正文中的指令应使用祈使语气（例如“运行脚本”“读取文件”），而不是被动/建议式表达（例如“脚本应该被运行”“可以读取该文件”）。

**证据标准**：引用具体句子，指出其被动/建议式问题，并给出祈使语气的改写建议。

**判定**：

- PASS：关键指令以祈使语气为主
- FAIL：多条关键指令使用被动/间接表述

### R21 — 避免含糊用语（S3）

**检查**：扫描是否存在犹豫/含糊限定词，尤其出现在可执行步骤里："consider"、"you might"、"perhaps"、"maybe"、"try to"、"it would be good to"、"ideally" 等。

**证据标准**：引用包含含糊用语的行并给出行号。

**判定**：

- PASS：指令中没有明显含糊用语
- FAIL：含糊用语出现在可执行指令中（背景说明除外）

### R23 — 指令需要解释“为什么”（S2）

**检查**：关键指令应包含理由/动机（"做 X 因为 Y"），而不仅是“要做什么”。

**证据标准**：找出缺少理由的关键指令并引用；给出如何补充理由的建议。

**判定**：

- PASS：多数关键指令给出了理由，或理由从上下文即可自证
- FAIL：多条重要指令缺少任何理由

---

## D5 精确性与可执行性

### R24 — 步骤应具备可验证的成功标准（S2）

**检查**：工作流步骤应说明如何判断已完成/成功。仅写“运行脚本”不够；应包含可验证条件（例如“确认输出中没有 FAIL 条目”）。

**证据标准**：引用缺少成功标准的步骤。

**判定**：

- PASS：多数步骤有明确或清晰可推断的成功标准
- FAIL：多条步骤缺少完成/成功判据

### R25 — 命令与路径必须具体可执行（S2）

**检查**：所有命令、文件路径、工具引用应具体可执行，避免占位符式或无法解析的表达。

**证据标准**：引用存在占位符（例如 `<command>`、未定义的 `$SOME_VAR`）或不可执行路径的内容。

**判定**：

- PASS：命令与路径均具体可执行
- FAIL：存在未解析占位符或不可执行引用

### R26 — 提到的操作必须给出具体方法（S1）

**检查**：当 skill 提到“验证 X”“检查 Y”时，必须说明怎么做：具体脚本、具体命令，或清晰的操作步骤。

**证据标准**：引用缺少方法细节的操作描述。

**判定**：

- PASS：所有操作都有具体方法
- FAIL：至少有 1 个操作被提到但没说明怎么做

### R27 — 必须定义完成标准（S2）

**检查**：skill 应明确整体任务何时算完成：最终交付物是什么？用户如何确认已完成？

**证据标准**：引用完成标准的文字；如不存在，说明缺失。

**判定**：

- PASS：存在清晰的完成标准
- FAIL：未定义完成标准

---

## D6 工作流完整性

### R28 — 必须定义清晰的分步工作流（S1）

**检查**：skill 必须包含结构化工作流：编号步骤、有序阶段或清晰的顺序化流程。

**证据标准**：指出工作流结构在哪里；如不存在，说明该 skill 应如何组织流程。

**判定**：

- PASS：存在清晰有序的工作流
- FAIL：缺少可辨识的分步流程，指令零散无序

### R29 — 工作流步骤之间应衔接顺畅（S2）

**检查**：前一步的输出应自然成为后一步的输入，不应出现上下文断裂或“跳步”。

**证据标准**：指出断裂位置：哪一步缺少可传递的产出/输入。

**判定**：

- PASS：步骤间数据/控制流清晰
- FAIL：存在衔接断裂或信息缺失

### R30 — 需包含错误处理或失败恢复（S2）

**检查**：skill 应说明出错时怎么办：脚本失败、缺文件、输入非法、状态异常等。

**证据标准**：引用错误处理文字；如不存在，说明缺失。

**判定**：

- PASS：至少描述了基础错误处理
- FAIL：完全未提及错误场景或恢复路径

### R31 — 条件分支必须完整描述每条路径（S2）

**检查**：当存在 if/else 条件路径（例如“如果 X 存在做 A，否则做 B”），每个分支都必须有明确指令。

**证据标准**：引用条件逻辑，并指出缺失/不充分的分支。

**判定**：

- PASS：所有分支都有清晰指令，或不存在条件分支
- FAIL：至少有 1 条分支缺失或描述不充分

---

## D7 模式与最佳实践

### R32 — 渐进式披露结构（S3）

**检查**：skill 应采用分层结构：

1. **入口**：顶部有简要概述
2. **正文**：详细步骤与工作流
3. **引用**：深度细节放在独立参考文件中

**证据标准**：描述文档结构是否符合该分层模式。

**判定**：

- PASS：结构从概述到细节再到引用分层清晰
- FAIL：信息层级扁平或倒置（深度细节先于概述）

### R33 — 验证优先使用确定性脚本（S3）

**检查**：验证类任务（正确性/格式校验等）应尽量使用确定性脚本，而不是完全依赖 LLM 主观判断。

**证据标准**：指出验证任务以及它们是否使用脚本/确定性检查。

**判定**：

- PASS：关键验证任务使用脚本或确定性检查
- FAIL：验证完全依赖 LLM 判断，缺少确定性手段

### R51 — 多选项场景需给出默认推荐（S2）

**检查**：当 skill 提供多个选项/替代方案时，应明确标注默认或推荐选项（例如“(recommended)”“优先 X”“默认：Y”）。

**证据标准**：引用提供选项的段落，说明是否标注默认/推荐。

**判定**：

- PASS：所有多选项段落都有默认/推荐，或不存在多选项
- FAIL：给出选项但未提供选择指引

---

## D9 脚本与代码质量

### R42 — 脚本包含基础错误处理（S2）

**检查**：`scripts/` 下脚本应包含：

- 对可能失败的操作使用 try/except（或等价处理）
- 失败时输出有意义的错误信息
- 失败时返回非 0 退出码

**证据标准**：引用错误处理代码；如缺失，指出缺失点。

**判定**：

- PASS：具备基础错误处理
- FAIL：缺少 try/except，可能静默失败
- SKIP：目标 skill 不存在 `scripts/` 目录

### R50 — 脚本能优雅处理缺失依赖（S2）

**检查**：脚本若导入非标准库模块或调用外部工具，应处理依赖缺失情况：对 import 做 try/except，或在使用前做显式检查并给出清晰提示。

**证据标准**：引用 import 语句并说明缺失依赖时是否会给出友好提示；如不友好，指出原因。

**判定**：

- PASS：仅使用标准库，或对非标准库依赖做了保护并提供清晰提示
- FAIL：存在未保护的非标准库依赖，缺失时会以晦涩 traceback 崩溃
- SKIP：目标 skill 不存在 `scripts/` 目录

## D0 附加检查

### R44 — Fork 类 skill 必须包含明确的任务指令（S2）

**检查**：当 `context: fork` 设置时，skill 正文必须包含对被派生 agent 的明确任务指令。

**证据标准**：引用 fork 任务指令；如不存在，说明缺失。

**判定**：

- PASS：存在清晰的任务委派指令
- FAIL：设置了 fork，但缺少对 agent 的任务说明
- SKIP：未设置 `context: fork`

---

## 自校验清单

完成全部语义检查后，必须对你自己的输出执行这些验证：

1. **Snippet 匹配**：每个 `evidence.snippet` 必须是目标 skill 的逐字摘录，并能在源文件中定位到。
2. **唯一性**：不允许两条 finding 的 `message` 完全相同；如重复，合并或区分。
3. **特指性**：每条 `message` 与 `suggested_fix` 必须引用该目标 skill 的具体内容（名称/短语/结构）。仅给“改进描述”这类泛化建议视为无效。
