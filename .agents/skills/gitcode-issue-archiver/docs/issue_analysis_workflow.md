# Bug-Report Issue 分析流程

本文档描述 AI 如何分析归档的 Bug-Report Issue，生成 PyPTO 不支持场景报告。

---

## 一、分析目标

### 1.1 核心目标
- 分析归档文件夹下的 Bug-Report issue
- 提取 PyPTO 不支持的场景
- 生成 agent 学习资料（检索目录）

### 1.2 图片处理要求
- **issue 中的图片也要看**，通过 OCR 技术解析图片内容
- 使用 read 工具读取图片文件
- 提取图片中的错误信息、代码、日志等关键内容

---

## 二、分析原则

### 2.1 不要臆想
- ❌ **禁止**：严格按照 issue 里实际提到的规避方式描述
- ❌ **禁止**：添加任何臆想的 API 或接口
- ✅ **要求**：只提取 issue 中明确提到的内容

### 2.2 详细但精简
- ✅ **错误信息**：精简描述（如"精度异常"）
- ✅ **根因分析**：详细说明
- ✅ **规避方案**：详细说明具体步骤

### 2.3 引用来源
- ✅ 每个结论都标注来源（评论编号/问题描述）
- ✅ 格式：`来源：Issue #XXX (closed)` 或 `来源：Issue #XXX 评论 #3`

---

## 三、分析步骤

### 步骤 1：读取归档记录
```python
# 读取 archive_record.json
record = read(archive_dir / "archive_record.json")
```

### 步骤 2：筛选 Bug-Report Issue
```python
# 筛选条件
bug_issues = [
    issue for issue in record["issues"].values()
    if issue["exists"] 
    and "[Bug-Report" in issue["title"]
]
```

### 步骤 3：逐个分析 Issue

对于每个 Bug-Report Issue：

#### 3.1 读取 issue 内容
```python
issue_file = read(archive_dir / f"issue-{number}.md")
```

#### 3.2 解析 issue 元素
- **标题**：提取问题概述
- **状态**：open / closed / closed resolved
- **描述**：问题详细说明
- **评论**：讨论过程、解决方案

#### 3.3 处理图片（如有）
```python
# 检查是否有图片引用
if "assets/issue-{number}" in issue_content:
    # 读取图片
    images = list_assets(archive_dir / "assets" / f"issue-{number}")
    for image in images:
        # 使用 read 工具读取图片（支持 OCR）
        image_content = read(image)
        # 提取关键信息
```

#### 3.4 提取关键信息
从 issue 中提取：
- **问题现象**：错误信息、异常行为
- **触发条件**：如何复现
- **根因分析**：为什么会发生
- **规避方案**：如何解决或规避
- **当前状态**：是否已修复

### 步骤 4：分类整理

按以下类别分类：

#### A. 编译错误类
- 编译失败、链接错误等

#### B. 运行时错误类
- 执行失败、崩溃、卡死等

#### C. 精度问题类
- 结果不对、数值异常、精度验证失败等

#### D. 性能问题类
- 耗时过长、性能劣化等

#### E. 功能缺失类
- 不支持的操作、缺少的接口等

#### F. 文档问题类
- 文档错误、缺失、不清晰等

#### G. 其他问题类
- 未分类的问题

### 步骤 5：生成报告

按照指定格式生成报告（见第四部分）。

---

## 四、报告格式要求

### 4.1 文档结构

```markdown
# PyPTO 不支持场景与问题检索目录

> **文档说明**: 本文档基于 GitCode Issue 归档自动生成
> **更新时间**: YYYY-MM-DD
> **数据来源**: 归档目录路径

## 第一部分：明确的不支持场景清单

本部分列出 PyPTO 明确不支持的场景及规避方案。

### 1. [场景分类] - [场景名称]

**不支持场景**：[简短描述]
- **触发条件**：[什么情况下会触发]
- **规避方案**：[具体的解决方法]
- **状态**：[仍需规避 / 已修复]
- **来源**：Issue #XXX (closed)

## 第二部分：问题现象索引

本部分包含所有 Bug-Report Issue，按类型分类。

### A. 编译错误类

**Issue 数量**: XX

#### Issue #XXX - [问题标题] [状态]

- **现象**: [简短描述]
- **触发条件**: [如何触发]
- **状态**: closed / open
- **来源**: Issue #XXX
```

### 4.2 状态标注规则

| 状态 | 含义 | 标注 |
|------|------|------|
| closed | 已关闭 | `[closed]` |
| open | 仍开启 | `[open]` |
| closed, resolved | 已修复 | `[closed, resolved]` |

**重要**：
- `resolved` 表示已修复，写法已支持，无需规避
- 未标注 `resolved` 的 closed issue 仍需规避

### 4.3 内容组织原则

#### 当 issue 描述清楚时
- ✅ 提取总结不支持场景
- ✅ 放入第一部分"明确的不支持场景清单"
- ✅ 提供详细的规避方案

#### 当 issue 描述不清时
- ✅ 简短描述现象
- ✅ 放入第二部分"问题现象索引"
- ✅ 不强行总结不支持场景

## 五、输出要求

### 5.1 输出文件（两个独立文件）

#### 文件一：不支持场景清单（开发前查看）
- **文件名**：`pypto_unsupported_scenarios.md`
- **位置**：`.agents/skills/gitcode-issue-archiver/docs/`
- **内容**：
  - 明确的不支持场景清单
  - 每个场景包含：触发条件、规避方案、状态、来源
- **用途**：开发前查看，了解已知限制

#### 文件二：问题现象索引（精度问题时检索）
- **文件名**：`pypto_issue_index.md`
- **位置**：`.agents/skills/gitcode-issue-archiver/docs/`
- **内容**：
  - 按类型分类的所有问题索引
  - 每个问题包含：现象、触发条件、状态、来源
- **用途**：遇到精度问题时，检索相似问题

### 5.2 质量要求（重要）

#### 文件一质量标准（严格执行）

**必须满足**：
- ✅ 只包含有**明确触发条件**的场景
- ✅ 触发条件要具体、可操作（不是"见 Issue 描述"）
- ✅ 规避方案要明确（不是"见讨论区"）
- ✅ 能让开发者快速判断是否会遇到此问题
- ✅ 能让开发者知道如何规避

**禁止包含**：
- ❌ 触发条件模糊的场景（如"使用该功能"、"见 Issue 描述"）
- ❌ 只有标题没有具体触发条件的
- ❌ 规避方案模糊的（如"见 Issue 讨论区寻找解决方案"）
- ❌ 附录内容（筛选规则说明等）

**宁缺毋滥原则**：
- 如果 issue 描述不清楚，不要放入文件一
- 宁可少一些，也要保证质量
- 数量少但质量高 > 数量多但质量低

#### 文件二质量标准

**按类型分类组织**：
- ✅ A-G 共 7 大类
- ✅ 每个 issue 标注：现象、触发条件、状态、来源
- ✅ 便于快速检索
- ❌ 不包含附录

### 5.3 用途定位

**文件一（不支持场景清单）**：
- ✅ 开发前必读
- ✅ 快速了解限制
- ✅ 避免踩坑
- ✅ 简洁明了，只包含高质量场景

**文件二（问题现象索引）**：
- ✅ 遇到问题时检索
- ✅ 查找相似案例
- ✅ 参考规避方案
- ✅ 完整的问题索引

#### 文件一格式：

## 六、示例分析

### 示例 1：精度问题

**Issue #108 - 合轴配置精度问题**

分析过程：
1. 读取 issue 描述：用户报告精度异常
2. 查看评论：发现是内存不连续导致
3. 提取规避方案：不对不连续tensor开启合轴
4. 标注状态：closed（未修复）

生成内容：
```markdown
### 1. 内存连续性 - 合轴优化

**不支持场景**：对内存不连续的 tensor 开启合轴优化
- **触发条件**：view/slice 后的 tensor，内存不连续
- **规避方案**：不对内存不连续的 tensor 调用 `set_operation_config(combine_axis=True)`
- **状态**：仍需规避
- **来源**：Issue #108 (closed)
```

### 示例 2：功能缺失

**Issue #265 - 不支持conv算子**

分析过程：
1. 读取 issue 描述：需要卷积操作但未找到
2. 查看状态：open
3. 提取信息：PyPTO 不支持 conv 算子

生成内容：
```markdown
### 8. 卷积算子 - Conv

**不支持场景**：不支持 conv 算子
- **触发条件**：需要使用卷积操作
- **规避方案**：等待功能支持
- **状态**：功能缺失
- **来源**：Issue #265 (open)
```

## 七、注意事项

### 7.1 分析边界

#### 问题类型筛选
- ✅ 只分析 Bug-Report 类型的 issue
- ❌ 不分析 Question、Requirement 等其他类型

#### 问题领域筛选
**✅ 需要关注的问题领域**：
- **PyPTO 写法问题**：API 使用错误、语法错误、约束违反等
- **Pass 问题**：编译优化、图优化、内存复用等 Pass 相关问题
- **Machine 问题**：底层实现、硬件映射、指令生成等 Machine 相关问题
- **精度问题**：计算结果错误、数值异常等
- **性能问题**：性能劣化、优化机会等
- **功能缺失**：不支持的操作、缺少的接口等

**❌ 需要过滤的环境类问题**：
- **安装配置问题**：环境搭建、包安装、依赖冲突等
  - 示例：`pip install 失败`、`CANN 安装问题`、`驱动版本不匹配`
- **编译环境问题**：编译器版本、工具链配置等
  - 示例：`g++ 版本不兼容`、`cmake 找不到`
- **硬件环境问题**：NPU 卡、驱动、固件等
  - 示例：`npu-smi 检测失败`、`驱动加载失败`
- **文档问题**：文档错误、描述不清等
  - 示例：`文档路径错误`、`示例代码过时`
- **工具问题**：第三方工具、测试框架等
  - 示例：`test framework 问题`、`日志工具问题`

**判断标准**：
```
如果问题根源在 PyPTO 代码/编译/运行 → ✅ 需要分析
如果问题根源在外部环境/工具 → ❌ 过滤掉
```

### 7.2 内容准确性
- ✅ 必须基于 issue 实际内容
- ✅ 不添加 issue 未提及的信息
- ✅ 不推断未明确说明的原因

### 7.3 图片处理
- ✅ 使用 read 工具的 OCR 能力
- ✅ 提取图片中的代码、错误日志、数据等
- ✅ 将图片内容整合到分析结果中

### 7.4 引用规范
- ✅ 标注 issue 编号和状态
- ✅ 标注评论编号（如来自评论）
- ✅ 格式统一：`Issue #XXX (状态)`

## 八、工作流程总结

```
归档完成
    ↓
询问用户：是否分析 Bug-Report Issue?
    ↓ (选择 yes)
读取 archive_record.json
    ↓
筛选 Bug-Report issue
    ↓
应用问题领域筛选规则
    ├─ ✅ 保留 PyPTO 写法/Pass/Machine 问题
    └─ ❌ 过滤环境类问题
    ↓
遍历保留的 issue
    ├─ 读取 issue-{num}.md
    ├─ 处理图片（OCR）
    ├─ 提取关键信息
    └─ 分类整理
    ↓
生成两个报告文件
    ├─ 文件一：pypto_unsupported_scenarios.md
    │   └─ 明确的不支持场景清单（开发前查看）
    └─ 文件二：pypto_issue_index.md
        └─ 问题现象索引（精度问题时检索）
    ↓
保存到项目根目录
```
