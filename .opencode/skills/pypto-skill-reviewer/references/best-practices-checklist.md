# 最佳实践审查清单

基于 Anthropic 官方文档的 10 维度审查清单，用于审查 PyPTO skill 质量。
每个维度包含具体的通过/不通过判定标准。

---

## 维度 1：Frontmatter 质量

Frontmatter 是 skill 可发现性的门控。description 失败意味着 skill 永远不会被触发。

### 检查项

| # | 检查内容 | 通过 | 不通过 |
|---|---------|------|--------|
| 1.1 | `name` 字段存在且使用小写+连字符 | `pypto-code-tracer` | `PyPTO Code Tracer`、缺失 |
| 1.2 | `name` ≤ 64 字符 | 20 字符 | 70 字符 |
| 1.3 | `name` 使用动名词形式（推荐但非必需） | `reviewing-pypto-skills` | `pypto-skill-reviewer`（可接受） |
| 1.4 | `description` 存在且非空 | 有内容 | 缺失或 TODO |
| 1.5 | `description` ≤ 1024 字符 | 200 字符 | 1500 字符 |
| 1.6 | `description` 使用第三人称 | "审查 skill 是否符合..." | "我来审查 skill..." |
| 1.7 | `description` 包含 WHAT（做什么） | "审查 PyPTO skill" | 只说何时使用 |
| 1.8 | `description` 包含 WHEN（何时触发） | "适用于审查单个 skill..." | 无触发上下文 |
| 1.9 | `description` 包含触发关键词 | "审查skill, review skill" | 仅通用术语 |
| 1.10 | 无非标准 frontmatter 字段 | 仅 `name`、`description` | `license`、`version`、`author` |

### 评分
- 1.1-1.8 全部通过 → ✅
- 1-2 项次要缺失（1.3、1.9、1.10）→ ⚠️
- 1.1、1.4、1.5、1.6、1.7、1.8 中任一不通过 → ❌

---

## 维度 2：简洁性与 Token 效率

skill 中的每个 token 都在争夺上下文窗口空间。对每段内容提出质疑。

### 检查项

| # | 检查内容 | 通过 | 不通过 |
|---|---------|------|--------|
| 2.1 | SKILL.md < 500 行 | 200 行 | 600 行 |
| 2.2 | body 中不重复 description 内容 | body 提供新信息 | "概述"节重述 description |
| 2.3 | 不解释 agent 已知的概念 | 假设 agent 有基础能力 | 解释 Git 是什么、JSON 是什么 |
| 2.4 | 该用表格/列表时不用冗长段落 | 结构化数据用表格 | 用段落列举选项 |
| 2.5 | 无注释掉的或占位符内容 | 内容完整干净 | `[TODO: ...]`、`<!-- ... -->` |
| 2.6 | 每个章节提供独特价值 | 各节内容不重叠 | 跨节内容重复 |

### 评分
- 全部通过 → ✅
- 2.1 在 500-600 行范围 或 1-2 处轻微冗余 → ⚠️
- 2.1 > 600 行 或 严重冗余 → ❌

---

## 维度 3：渐进披露

三级结构：元数据 → 指令 → 资源。

### 检查项

| # | 检查内容 | 通过 | 不通过 |
|---|---------|------|--------|
| 3.1 | SKILL.md 聚焦指令，细节放在 references/ | 清晰分离 | 所有内容堆在一个文件 |
| 3.2 | 引用文件距 SKILL.md 仅一级深度 | `references/foo.md` | `references/sub/deep/foo.md` |
| 3.3 | 长文件(>200行)有导航（目录或节链接） | 有目录 | 无导航辅助 |
| 3.4 | 引用文件有显式读取指令 | `→ 读取: $SKILL_DIR/references/...` | 只提及文件存在 |
| 3.5 | 信息放在正确层级（高层在 SKILL.md，细节在 refs） | 主文件放摘要，refs 放细节 | SKILL.md 中放详细 API 文档 |

### 评分
- 全部通过 → ✅
- 轻微导航缺失或层级略有错位 → ⚠️
- 完全没有渐进披露（所有内容在 SKILL.md >500 行） → ❌

---

## 维度 4：内容规范

语言一致性、术语和结构约定。

### 检查项

| # | 检查内容 | 通过 | 不通过 |
|---|---------|------|--------|
| 4.1 | 结构元素语言一致 | 所有标题使用同一种语言 | 中文标题与英文标题混杂 |
| 4.2 | 指令使用祈使句/动词不定式 | "读取文件"、"运行命令" | "你应该读取文件" |
| 4.3 | 无时效性信息 | 无时限的指引 | "截至 2024 年..."、"目前..." |
| 4.4 | 全文术语一致 | 同一概念用同一术语 | "skill"/"插件"/"扩展"交替使用 |
| 4.5 | body 中无"何时使用"节 | 触发条件仅在 description 中 | 出现 "## 使用场景" 或 "## 触发场景" |
| 4.6 | 代码块有语言标签 | ````python`、````bash` | 无标签的 ```` ``` ```` |

### 评分
- 全部通过 → ✅
- 1-2 处轻微一致性问题 → ⚠️
- body 中出现"何时使用"或普遍语言混杂 → ❌

---

## 维度 5：自由度匹配

指令精确度与任务脆性匹配。

### 检查项

| # | 检查内容 | 通过 | 不通过 |
|---|---------|------|--------|
| 5.1 | 高脆性任务有精确命令/脚本 | `git push origin HEAD` | "推送你的更改" |
| 5.2 | 中脆性任务有伪代码/结构化步骤 | 编号工作流步骤 | 模糊的段落描述 |
| 5.3 | 低脆性任务使用文字指引 | "使用清晰的变量名" | 对主观任务过度规定 |
| 5.4 | 不过度规定灵活任务 | 写作风格用指引 | commit message 用精确模板 |
| 5.5 | 不欠规定刚性任务 | 精确的 API 端点和参数 | "调用 API"但不给参数 |

### 评分
- 全文精确度匹配恰当 → ✅
- 1-2 处轻微不匹配 → ⚠️
- 系统性精确度错误 → ❌

---

## 维度 6：工作流与反馈环

复杂任务需要检查清单和验证循环。

### 检查项

| # | 检查内容 | 通过 | 不通过 |
|---|---------|------|--------|
| 6.1 | 多步流程有编号/有序步骤 | `### 第 1 步:`、`### 第 2 步:` | 无序段落描述顺序流程 |
| 6.2 | 关键操作有验证步骤 | "验证：运行 `X`，期望 `Y`" | 重要操作后无验证 |
| 6.3 | 易出错步骤有反馈环 | "若失败 → 修复 → 重试" | 线性流程无错误恢复 |
| 6.4 | 决策点有清晰分支 | "若 X → 做 A；否则 → 做 B" | 模糊的"酌情处理" |
| 6.5 | 结束状态明确定义 | "完成标志：报告生成、评分计算完毕" | 无完成标准 |

### 评分
- 所有适用项通过 → ✅
- 缺少 1-2 个验证步骤 → ⚠️
- 复杂流程无工作流结构 → ❌

---

## 维度 7：常用模式

恰当使用已建立的 skill 模式。

### 检查项

| # | 检查内容 | 通过 | 不通过 |
|---|---------|------|--------|
| 7.1 | 固定结构输出使用模板模式 | 报告模板、commit 消息模板 | 结构化数据用自由格式输出 |
| 7.2 | 演示用法时使用示例模式 | 具体的请求 → 响应示例 | 仅抽象描述 |
| 7.3 | 分支逻辑使用条件工作流 | 决策树、if/then 表格 | 嵌套的段落条件 |
| 7.4 | 参数/选项查阅使用速查表 | 紧凑的表格 | 长段落列举选项 |
| 7.5 | 复杂流程使用 Mermaid 图（可选加分项） | 可视化工作流辅助 | N/A（非必需） |

### 评分
- 使用了恰当的模式 → ✅
- 错过 1-2 个模式使用机会 → ⚠️
- 任务类型使用了错误模式 → ❌

---

## 维度 8：反模式检测

已知的降低 skill 质量的坏实践。

### 检查项

| # | 检查内容 | 通过 | 不通过 |
|---|---------|------|--------|
| 8.1 | 无硬编码绝对路径 | `$SKILL_DIR/scripts/`、`$UNIFIED_SKILLS_ROOT` | `/workspace/code/skills/library/shared/...` |
| 8.2 | 无 Windows 风格路径 | 仅正斜杠 | `C:\Users\...`、反斜杠 |
| 8.3 | 多选项时有默认推荐 | 高亮推荐默认值，列出替代项 | 5 个选项无推荐 |
| 8.4 | 无深度嵌套引用链 | SKILL.md → ref（最多 1 跳） | SKILL.md → ref → sub-ref → sub-sub-ref |
| 8.5 | 已发布 skill 无占位符/TODO 内容 | 内容完整干净 | `[TODO: ...]`、`[PLACEHOLDER]` |
| 8.6 | 无过度冗长的解释 | 简洁指令 | 多段落解释简单概念 |
| 8.7 | 跨文件无重复信息 | 单一信息源 | 同一表格在 SKILL.md 和 reference 中都出现 |

### 评分
- 未发现反模式 → ✅
- 1-2 处轻微反模式 → ⚠️
- 存在硬编码路径或已发布 skill 有占位符 → ❌

---

## 维度 9：脚本/代码质量

skill 中打包的自动化脚本。

### 检查项

| # | 检查内容 | 通过 | 不通过 |
|---|---------|------|--------|
| 9.1 | 脚本有错误处理 | `set -e`、try/except、退出码 | 无错误处理 |
| 9.2 | 脚本中的常量/配置有注释说明 | 注释解释魔法数字 | 无解释的硬编码值 |
| 9.3 | 脚本使用环境变量表示路径 | `${SKILL_DIR}`、`${UNIFIED_SKILLS_ROOT}` | 硬编码 `/workspace/...` |
| 9.4 | 脚本可执行且有 shebang | `#!/usr/bin/env python3` | 缺少 shebang |
| 9.5 | 脚本优雅处理缺失的依赖 | 使用前检查，给出有用的错误信息 | 缺少工具时直接崩溃 |

### 评分
- 所有适用项通过 → ✅（无脚本则 N/A）
- 轻微问题（缺少注释、部分错误处理）→ ⚠️
- 无错误处理或脚本中有硬编码路径 → ❌

---

## 维度 10：文件组织

目录结构和文件命名。

### 检查项

| # | 检查内容 | 通过 | 不通过 |
|---|---------|------|--------|
| 10.1 | 描述性文件名 | `best-practices-checklist.md` | `ref1.md`、`data.md` |
| 10.2 | 目录使用恰当 | scripts/ 放代码，references/ 放文档 | 所有文件放根目录 |
| 10.3 | 无多余文件 | 仅被引用或使用的文件 | 孤立文件、example_asset.txt |
| 10.4 | SKILL.md 中记录了可用文件 | 资源表或文件清单 | 文件存在但未提及 |
| 10.5 | 命名约定一致 | 全部小写+连字符 | 大小写混用、下划线 |

### 评分
- 全部通过 → ✅
- 1-2 处轻微命名问题 → ⚠️
- 存在孤立文件或无文件说明 → ❌
